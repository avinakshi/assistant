An interview copilot desktop app that listens to your interviewer's voice, transcribes it, detects
when they ask a question, and streams a natural-sounding answer to an overlay that is invisible
to screen recording software -- all within one second.

It is more affordable than Parakeet AI (799­1,599/month vs Parakeet's ~$30 per three

two features no competitor ships: voice-agent practice mode and AI-scored post-session review.

It is positioned as a practice and preparation copilot for job seekers, not a cheating tool -- the
marketing, ToS, and first-run consent all reinforce this posture.

Part 1 -- Product vision

What it is: A real-time interview copilot, desktop-first (Mac + Windows), with a companion web
app and a secondary Chrome extension.
What it does during a live interview:

  1. Captures the system audio (interviewer's voice) via OS-native APIs
  2. Streams it to Deepgram for real-time transcription
  3. Detects when the interviewer asked a question
  4. Sends the question + context (resume, JD, recent transcript) to Claude/GPT-5/Gemini via

      prompt cache
  5. Streams a conversational, Indian-English-sounding answer to a stealth overlay
  6. All of this in under 900 milliseconds from question-end to first word of answer visible
  7. The overlay is invisible to Zoom, Teams, Meet, OBS, QuickTime, and all screen recording

      APIs

What it also does:
      Practice mode with voice agents (mock interviews)
      Post-session AI review with scoring
      Auto-detects meetings
      Supports 10+ languages for transcription (English-first, expanding to Hindi, Telugu, Tamil,
      Kannada, Marathi, Bengali, Gujarati, Malayalam, Punjabi)

5.4 Question detector
Purpose: Decide when to fire the LLM. Not every transcript is a question.
Location: packages/question-detector/src/index.ts
Input: { text: string, prevAnswerEndedAt: number | null, userSpokeRecently: boolean

}

Output: { isQuestion: boolean, confidence: number, hint:

'behavioral'|'coding'|'system_design'|null }

Heuristics (v1):
Returns isQuestion: true if ANY of:

      Ends with ?
      Starts (case-insensitive) with: tell me , describe , walk me through , how would you ,
       how do you , what would you , why did you , explain , can you , have you ever , give
      me an example , what's your , talk about , imagine , share a time , share an

       instance

      Coding trigger: implement , write a function , write code , given an array , given a
      string , given a tree , complexity , big o
      System design trigger: design a system , design twitter , design uber , design
      youtube , how would you design , architect a , scale to

Returns isQuestion: false if:
      Less than 4 words
      Only acknowledgment: ok , okay , got it , makes sense , thanks , sure , right , mm
      hmm , yeah
      Last assistant answer ended < 15 seconds ago AND transcript uses first-person pronouns
      ("I", "my", "me")  likely the candidate still speaking

Hint classification:
      Coding triggers  coding
      System design triggers  system_design
      Everything else  behavioral

v2 (later): Fine-tuned DistilBERT classifier trained on ~10k labeled interview transcripts. Runs

5.7 Screen OCR (coding mode)
Purpose: Read a coding problem off the user's screen.

Pipeline:

  1. Rust sidecar captures screenshot via CGDisplayCreateImage (Mac) or BitBlt (Win)
  2. Downscale to max 1920×1080, PNG encode
  3. POST to /api/ocr/coding-problem (multipart)
  4. Backend: SHA256 hash  check Redis cache  if miss: Google Cloud Vision

       TEXT_DETECTION

  5. Parser attempts to extract LeetCode/HackerRank layout:
            Title (first matching ^\d+\.\s+ pattern)
            Description
            "Example 1:" blocks  structured examples
            "Constraints:"  list

  6. Return CodingProblem object
  7. Frontend feeds it to coding prompt pack along with the user's request

Caching: SHA256 of PNG  parsed JSON, TTL 24h.
Cost control: rate limit 10 OCR/min per user to prevent accidental loops.

5.8 Practice mode
Purpose: Let users practice without a real interviewer.
Flow:
  1. User picks: role, company (optional), difficulty, duration (10/20/30 min)
  2. LLM generates question plan (~8-12 questions with rubrics) via non-streaming call
  3. Agent greets user via TTS (Cartesia Sonic, ~200ms latency)
  4. Agent reads first question
  5. User answers; STT captures via mic (not system audio -- practice uses mic input)
  6. Silence detection ends answer
  7. LLM decides follow-up (30% for behavioral, 60% for system design) or move on
  8. Repeat for all questions
  9. At end: TTS thanks user, explains report is generating

10. BullMQ job: score each answer against rubric, generate report

Scoring per question:
      Specificity 0-5
      Structure 0-5
      Communication 0-5 (filler words, pace)
      Relevance 0-5

Report:
      Radar chart
      Per-question feedback ("Your situation was clear but you didn't quantify the outcome. Try:
      'reduced incidents by 40%' instead of 'improved things'.")
      Overall band: Poor / Developing / Strong / Excellent

Retry: user can retry individual questions.

Part 5 -- Coding conventions

TypeScript
       strict: true -- every project. No exceptions.
       noUncheckedIndexedAccess: true -- treats arr[i] as possibly undefined.

      Prefer named exports over default exports. Exception: Next.js pages, Electron entry files.

      enforces.

React

Part 9 -- Handling tricky scenarios

When audio capture doesn't work on a user's machine
Try in order:

  1. Check permission state (Mac: CGPreflightScreenCaptureAccess() )
  2. Show in-app permission guide with screenshots
  3. Detect device (some Windows headsets route call audio to device not default)
  4. Allow user to pick input device explicitly in settings
  5. Log to Sentry with device info (OS version, make, model)
  6. If still broken: fall back to "browser meetings only via extension" messaging

When LLM costs spike
Watch llm_tokens_generated_total metric. If spikes:

  1. Check cache hit rate -- should be > 80%. If not, audit prompt construction.
  2. Check if Free tier abuse -- someone scripting Free accounts
  3. Rate-limit per user more strictly on Free
  4. Downgrade Free from Gemini Flash to a smaller/cheaper model if needed
  5. If racing mode is too expensive: disable for a subset of Pro users until costs normalize

When a user reports "the overlay is showing in my screen share"
Collect:

  1. OS version
  2. App version
  3. Meeting platform
  4. Screen share method (share whole screen vs. window vs. tab)

Known failure modes:
      macOS 12.x (setContentProtection works but SCKit audio doesn't)
      Windows 10 < build 19041 (WDA_EXCLUDEFROMCAPTURE unavailable)
      Nvidia ShadowPlay / AMD ReLive (capture at GPU level, bypasses OS APIs)
      Some screen-recording apps using private APIs

Log all of these in Sentry. Update support docs with known limitations.

When Deepgram goes down
      Automatic failover to AssemblyAI after 3 consecutive 5xx in 60s
      Banner in overlay: "Using backup transcription service"
      Monitor Deepgram status page

When Claude goes down
      In Auto mode: GPT-5 wins by default (already racing)
      In manual Claude mode: fallback to GPT-5 with warning in overlay
      If both down: fall back to Gemini with quality warning

When a test is flaky
      Flaky tests are bugs. Fix them, don't skip them.
      If truly non-deterministic (timing in E2E): use proper waits, not sleep
      If test depends on external service: mock it with replay
      Three strikes: if a test is flaky-fixed 3 times, delete it and write a better one

Part 10 -- Common failure modes you'll see

"Rust crate builds but napi binary doesn't load in Electron"
      Check napi-rs version matches Electron's Node ABI
      Build with napi build --platform --release
      Binary must be in correct location: packages/audio-core/{platform}-{arch}.node
      Electron must load from process.resourcesPath in production, __dirname in dev

"ScreenCaptureKit throws ScreenRecording permission denied even though granted"
      App bundle ID in entitlements must match Electron's real bundle ID
      In dev: Electron runs as com.github.Electron . Entitlements must reference this OR you
      must codesign with your bundle ID locally.
      Fix: use a Dev Build Identity and sign locally with codesign --sign - --entitlements

       resources/entitlements.plist /path/to/Electron.app --deep

"setContentProtection(true) seems to do nothing on Mac"
      Must be called AFTER win.show() -- calling before is a no-op on some macOS versions
      Check macOS version -- requires 10.7+ but has behavioral differences across versions

"WDA_EXCLUDEFROMCAPTURE returns 0"
      User is on Windows build < 19041
      Degrade to WDA_MONITOR
      Surface error in Sentry with build number

"Deepgram disconnects after 5 minutes of silence"
      Add keepalive: {"type":"KeepAlive"} every 5 seconds
"Claude stream stalls at random points"
      You're waiting for message_stop instead of flushing on content_block_delta
      Flush tokens every 50ms batched

"Razorpay webhook signature always fails"
      Using wrong secret (webhook secret  key secret)
      Body must be exact bytes -- don't parse-then-restringify

"Electron renderer can't reach IPC"
      Check preload is loading: contextBridge.exposeInMainWorld('ic', { ... })
      Renderer uses window.ic.* , not require('electron')
      Channels must match main process registrations exactly

import WebSocket from 'ws'

import { config } from './config'

export class SessionWsClient {
   private ws: WebSocket | null = null
   private reconnectDelay = 1000

   async connect(): Promise<void> {
      const token = await getAccessToken()
      this.ws = new WebSocket(`${config.wsUrl}/ws/session?token=${token}`)

      this.ws.on('open', () => {
         this.reconnectDelay = 1000
         this.startFrameForwarding()

      })

      this.ws.on('message', (data, isBinary) => {
         if (isBinary) return // server never sends binary to client
         const msg = JSON.parse(data.toString())
         this.emitToRenderer(msg)

         if (msg.type === 'error' && msg.code === 'AUTH') {
            this.handleAuthError()

         }
      })

      this.ws.on('close', () => this.scheduleReconnect())
      this.ws.on('error', (err) => this.logError(err))
   }

   private startFrameForwarding() {
      AUDIO_CORE.onFrame((pcmBuffer) => {
         if (this.ws?.readyState === WebSocket.OPEN) {
            this.ws.send(pcmBuffer, { binary: true })
         }
      })

   }

   private async handleAuthError() {
      await refreshToken()
      this.connect() // reconnect with new token

   }

   private scheduleReconnect() {
      setTimeout(() => {
         this.reconnectDelay = Math.min(this.reconnectDelay * 2, 30000)
           this.connect()
        }, this.reconnectDelay)
     }
  }

Part 13 -- Handling known platform issues

macOS: "Electron wants screen recording access" re-prompts
Cause: macOS remembers permission per-app, and in dev Electron runs as a generic Electron
binary.
Fix (dev): move Electron.app to /Applications. Alternatively, use a local codesign with your app's
bundle ID.
Fix (prod): properly signed with your own Developer ID -- permission persists.

macOS: permission denied after OS update
Cause: macOS 14/15 sometimes revalidates Screen Recording permissions.
Fix: detect via CGPreflightScreenCaptureAccess() , prompt user to re-check. We re-check on
every session start.

Windows: WDA_EXCLUDEFROMCAPTURE returns 0 on older builds
Cause: Windows 10 < build 19041.
Fix: degrade to WDA_MONITOR which renders black in screen capture. Log user's build version.
Show one-time notice: "For full stealth, upgrade Windows."

Windows: Nvidia ShadowPlay / AMD ReLive bypass stealth
Cause: These capture at GPU level.
Fix: can't. Disclose in ToS: "Some third-party screen recording software (e.g., Nvidia ShadowPlay,
OBS with GPU capture) may bypass OS-level privacy APIs. The overlay may be visible in such
recordings."

Deepgram: intermittent 500 errors
Fix: automatic failover to AssemblyAI after 3 consecutive failures in 60s. Banner in overlay.

Claude: rate limit errors
Fix: back off, fall back to GPT-5. Sentry-alert on sustained errors.

Electron: renderer process OOM during long sessions
Cause: accumulated transcript + answer DOM nodes.
Fix: transcript display limited to last 20 items. Answer history kept in memory but rendered only
last 3.

This is the most important document in the set. The user explicitly wanted "test multiple

Part 1 -- Testing philosophy

We do not ship untested code. Ever. Every feature passes four testing passes before it is
considered done:

  1. Automated unit tests -- written alongside the code by Claude Code
  2. Automated integration tests -- written alongside the code, uses real or realistic-mocked

      services
  3. Manual smoke tests -- you, on real machines, with a real test checklist
  4. Regression pass -- run all prior phases' tests before moving to next phase

If any test is flaky or failing, the phase is not done. No exceptions. No "we'll fix it later." Later
never comes.

Part 6 -- Load testing (week 11 only)

Before launch, run a load test with k6:

   javascript
// scripts/load-test.js
import ws from 'k6/ws'
import { check } from 'k6'

export const options = {                // ramp to 50 concurrent sessions
   stages: [                            // hold
      { duration: '2m', target: 50 },   // burst
      { duration: '5m', target: 50 },   // hold
      { duration: '2m', target: 200 },  // ramp down
      { duration: '5m', target: 200 },
      { duration: '2m', target: 0 },
   ],

}

export default function () {
   const url = `${__ENV.WS_URL}/ws/session?token=${__ENV.TEST_JWT}`

   ws.connect(url, {}, function (socket) {
      socket.on('open', () => {
         // Send 50fps PCM frames for 3 minutes, simulate a session
         for (let i = 0; i < 9000; i++) {
            socket.sendBinary(new ArrayBuffer(640))
            sleep(0.02)
         }
      })
      socket.on('message', (data) => {
         const msg = JSON.parse(data)
         if (msg.type === 'answer.done') {
            check(msg, { 'latency reasonable': (m) => m.latencyMs < 3000 })
         }
      })

   })
}

Targets:

      200 concurrent live sessions supported
      p95 LLM first-token < 2s even under load
      0% WS connection drops
      Railway CPU < 80%, memory < 80%

If these fail, scale Railway up, add worker nodes, retest.

Things NOT to do

While running this plan, do NOT:
  Try to be on social media all day "building in public"
  Take meetings with investors (defer until post-launch)
  Hire anyone (stay lean)
  Redesign the brand twice
  Add features not in the spec
  Compare yourself daily to competitors on Twitter
  Work on weekends without rest (burnout kills companies)
  Skip exercise or sleep (these help you ship faster, not slower)

When you fall behind

You will fall behind sometimes. Here's what to do:
  1. Don't compress tests. Delay the phase by 1-2 days instead of skipping tests.
  2. Don't compress polish in Phase 7. Polish is what separates this from a prototype.
  3. Do compress Phase 10 (Chrome extension). It's secondary. Ship without it if you must.
  4. Do compress marketing content. You can do more in the week after launch.
  5. Don't compress Phase 11 (beta). This is where you discover what's actually broken.

If you're more than a week behind by end of Week 6: step back, reassess, cut scope. Lifetime plan
can be v1.1. Chrome extension can be v1.1. Post-session review PDF export can be v1.1. Don't cut:
audio capture, stealth, STT, LLM, payments, basic review.

The single most important reminder

Rest well. Eat well. Exercise. Sleep 7+ hours.

This plan requires 12 weeks of high-output work. You cannot fake this with coffee and all-
nighters. Every hour spent on your health is an hour of better code tomorrow.

Go build something great.
